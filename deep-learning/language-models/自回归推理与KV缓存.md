##### 自回归生成中的缓存

解码器按 $P(x_{1:T})=\prod_tP(x_t\mid x_{<t})$ 建模。预填充阶段同时计算完整提示中的表示；解码阶段每次追加一个 token。因果注意力下已有位置的键和值不会因后续 token 改变，因而可将每层历史 $K,V$ 保存在缓存中。新查询只需与缓存中的键计算注意力，再读出对应值；历史查询无需重新计算 [自回归缓存机制](https://huggingface.co/docs/transformers/cache_explanation)

设层数 $L$、批量 $B$、上下文长度 $T$、KV 头数 $H_{\mathrm{kv}}$、每头维度 $d$，每元素占 $b$ 字节。忽略对齐、元数据与中间激活，完整 KV 缓存约为 $2LBTH_{\mathrm{kv}}db$ 字节。取 $L=32,B=1,T=4096,H_{\mathrm{kv}}=8,d=128,b=2$，结果为 512 MiB。上下文或并发翻倍时该项近似翻倍，参数显存并不随之翻倍

##### 分组查询与长文处理

多头注意力让每个查询头拥有独立的 KV 头；分组查询注意力让若干查询头共享一组键和值。查询头数不变时，减少 KV 头数可以降低缓存占用和解码中的读取流量，实际吞吐还受硬件及批量限制。历史上下文多长，每次新 token 的完整注意力仍要访问多长的键值序列。缓存省去了重算，不保证任意长提示都具有固定首 token 延迟 [Grouped-Query Attention](https://arxiv.org/abs/2305.13245)

处理财报或公告时，首 token 时延往往受预填充和输入长度影响，持续生成速度还受缓存带宽影响。缓存复用要求模型版本、分词和可复用前缀一致；不同时间版本的公告必须保持数据隔离，以免把后续修订的内容提前提供给历史事件

上下文缓存改变单次推理的开销，参数更新及其目标函数见[监督微调与策略优化](监督微调与策略优化.md)
